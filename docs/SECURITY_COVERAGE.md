# Security coverage and resource boundaries

This document records the boundaries that the v0.4 alpha actually enforces. It is a coverage
map, not a security certification. A control is `covered` only when the implementation rejects
the condition and an automated test exercises that rejection. `Partial` means that a useful
limit exists but an adjacent path or aggregate budget is still open. `Open` means there is no
hard product-owned boundary yet.

## Coverage matrix

| Surface | Threat or failure mode | Enforced boundary and default | Automated evidence | Status |
| --- | --- | --- | --- | --- |
| File admission | Oversized, replaced, linked or non-regular input | `FileTrustPolicy` rejects files over 2 GiB by default, checks opened-handle identity, and rejects symlinks, parent symlinks and Windows reparse points unless explicitly allowed | `tests/test_content.py`, `tests/test_content_limits.py` | Covered for admission. The portable identity is metadata, not a persistent content digest. |
| ZIP and OOXML inspection | Entry floods, ZIP64 or EOCD disagreement, expansion bombs, traversal and extraction-name collisions | 4,096 entries, 16 MiB central-directory metadata, 256 MiB per member, 1 GiB aggregate expansion and ratio 200 by default. Central-directory structure is counted before `ZipFile` object creation. Windows separators, dot segments, trailing spaces or dots, ADS, device names, NFC and case folding are normalized or rejected. | `tests/test_content_limits.py` | Covered for pre-parse archive inspection. No archive is extracted by this component. |
| GZIP inspection | Forged footer, concatenated members, padding dilution and decompression CPU or memory abuse | At most 64 MiB compressed input is streamed through validation. The ZIP expansion limits also apply: 4,096 members, 256 MiB per member, 1 GiB total output and ratio 200. | `tests/test_content_limits.py` | Covered for content admission. Decompression is still in the calling process on the normal path. |
| JSON and JSON5 files | Deep recursion, wide structures, duplicate or string-colliding keys, non-finite or non-JSON values, huge fallback parse and unbounded write iterable | `JsonFileConnector` admits at most 64 MiB, limits JSON5 fallback parsing to 64 KiB, depth to 128 and aggregate object members plus array items to 100,000. Strict JSON identification rejects CPython's non-standard non-finite constants. Destination iterables stop at the item budget before a file write, Python tuples are counted as JSON arrays, object keys must already be strings, and combined existing plus new output is rechecked. | `tests/test_json.py`, `tests/test_content_limits.py`, `tests/test_content_differential.py`, `tests/test_json_test_suite.py` | Covered for these limits. The JSON and JSON5 parsers still run in the application process. |
| XML identification | Entity expansion, deep or wide trees and attribute bombs | Full safe parse is attempted only up to the 4 MiB text parse limit. Streaming gates cap depth at 128, elements at 100,000 and attributes per element at 1,024. A leading `<` alone is not accepted as XML. | `tests/test_content_limits.py` | Covered for content identification. Downstream document parsers remain in process. |
| Isolated content worker | Parser hang, crash, log flood, output flood and input replacement | Strict default policy requires an OS sandbox, with 15 s wall time, 10 s CPU, 512 MiB input, 512 MiB address space, 256 KiB stdout or response, 128 KiB stderr, 64 KiB parser log, 256 KiB output file, 512 MiB private tmpfs, 64 open files and 64 processes. Input and protocol snapshots are size and digest checked. | `tests/test_isolation.py`, `tests/test_parser_worker.py`, `tests/test_isolation_cli.py`, Linux sandbox CI lab | Covered for content inspection when the isolated API is used and the requested backend is available. It is not used for normal structured schema or record parsing. |
| Windows process worker | Child crash and wall-time or pipe-output exhaustion | Parent process enforces wall time and bounded stdout or stderr capture. Resource use is sampled when `psutil` is installed. | `tests/test_isolation.py`, `tests/test_isolation_cli.py` | Partial. A Windows subprocess is reported as `PROCESS`; there is no Job Object, AppContainer, hard RSS limit or descendant-tree guarantee. |
| Record wire protocol | Field-count, field-ciphertext and serialized-record amplification | `ProtocolLimits` defaults to 4,096 fields, 16 MiB ciphertext per field and 64 MiB serialized wire bytes. Relay, outbox and spool persistence recheck the wire limit. | `tests/test_agents.py`, `tests/test_source_auth.py`, `tests/test_outbox.py`, `tests/test_relay.py` | Partial. Bounds exist, but dedicated adversarial boundary tests for every default should remain part of the release gate. Python objects can exist before their serialized size is checked. |
| Recipient key authenticity | Control-plane key substitution, stale or forked rotation, retired-key reuse and unusable X25519 points | A separately pinned Ed25519 destination identity signs route, validity, generation, predecessor and X25519 key material. Persistent trust state accepts only generation 1 or the exact next link, retains at most 512 used key IDs and rejects A -> B -> A reuse. Key IDs canonicalize the X25519 u-coordinate so alternate RFC 7748 encodings cannot bypass reuse detection. Blank v3 key IDs, nonblank v2 key IDs and low-order keys fail by default. | `tests/test_recipient_auth.py` | Covered against an untrusted control plane while the source host state and independent identity-key provisioning remain trusted. Whole-file host rollback, identity-key rotation and emergency revocation remain open. |
| Source key hard revocation | A relay publishes an already verified record after hard revocation returns | Source-trust verification sessions hold one process-local registry lock across the full bounded enqueue or lease batch and its SQLite commit or rollback. Enqueue, lease and dead-letter transitions acquire trust before SQLite, so concurrent registry mutation has one lock order. Destination verification remains independent. | `tests/test_source_auth.py`, `tests/test_relay.py` | Covered for concurrent threads sharing one `SourceTrustStore`. Authenticated durable propagation and linearizability across separate processes remain deployment responsibilities. |
| Preflight input blast radius | A valid mapping unexpectedly targets far more source records than intended | `PreflightRunner` and the `prepare` or `preflight` CLI accept an explicit `max_input_records` / `--max-input-records` budget. They consume through the boundary, probe once, then emit a blocking finding before plan promotion or destination writes. A smaller diagnostic sample stops validation, not counting for the hard gate. | `tests/test_preflight.py`, `tests/test_cli.py` | Covered when an operator configures the budget. The alpha does not yet derive a safe threshold from recipe history or destination change counts. |
| Delivery state sequences | Reordered work, stale leases, restarts, lost acknowledgements, rollback, unknown write outcome and quarantine replay | A Hypothesis state machine composes real SQLite outbox, relay, ledger, spool, signed audit and event stores. Exact reference sets cover all three durable queues; receipt-specific audit and event tuples cover status, reason, digest and correlation. Required fault transitions and successful quarantine replay are seeded before generated reordering. | `tests/test_delivery_state_machine.py`, `tests/test_workflow_failure_lab.py`, `tests/test_recovery_stress.py` | Covered for the local test connector and the orchestrated runtime contract. Relay and outbox low-level APIs cannot independently consult the destination ledger, so callers can still misuse them outside the driver. |
| Differential structured parsing | One parser accepts a structure whose safety scanner counts differently | 10,000 deterministic standard-JSON structures and representative JSON5 syntax are parsed by the library parser, counted independently, then compared with the pre-parse depth/item scanner at exact and one-below boundaries. Pinned JSONTestSuite and W3C CSVW subsets add external syntax and record-boundary evidence with per-file hashes. | `tests/test_content_differential.py`, `tests/test_json_test_suite.py`, `tests/test_w3c_csvw.py` | Partial. This covers JSON-like structural limits and selected CSV cases, not full semantic equivalence. XLSX has no accepted independent second parser; current Calamine allocation issues make an in-process differential dependency unsafe. |
| Workflow benchmark | Accidental unbounded synthetic run, batch or event history | Requested records are limited to 1 through 1,000,000 and batch size to 1 through 10,000. Latency sampling retains at most 10,000 samples. Before creating its workspace, the runner reserves 1 KiB for every possible record, batch, stage and lifecycle event against an explicit 64 MiB default event budget. The CLI exposes `--event-stream-max-mib` up to 1,024 MiB and the report records configured and reserved bytes. | `tests/test_workflow_benchmark.py`, `tests/test_workflow_end_to_end.py`, `tests/test_workflow_failure_lab.py`, `tests/test_observability.py` | Covered for the benchmark driver, not a global connector contract. The one-million-record setting fits the maximum event budget with the default batch size of 100, but not with every smaller batch size; incompatible combinations fail before work starts. |
| Destination runtime | Oversized, partially committed or downgrade-replayed delivery batch | `deliver_many` consumes at most 10,000 records and 64 MiB of sealed wire before either scalar or batch dispatch. It chunks only through an explicit connector capability, authenticates every record, preserves per-record identities and ledger fences, and requires an all-or-none write result. Durable `BATCH_*` and `REPLAY_*` states retain original batch membership and make older runtimes reject ambiguous rows instead of applying a weaker scalar replay rule. Capability changes, crashes directly after retry re-arming, replay rollback and pre-write replay failure keep that fence. SQLite and PostgreSQL batches are additionally capped at 1,000 records and 64 MiB. | `tests/test_runtime.py`, `tests/test_database.py`, `tests/test_spool_limits.py`, `tests/test_delivery_state_machine.py` | Covered for the runtime and built-in database batch path. Ledger upgrades are forward-only, not a mixed-version writer lock. A third-party batch connector is responsible for honestly implementing its advertised transaction and idempotency semantics. |
| HTTP JSON source | Response body flood and endless pagination | Each response is capped at 16 MiB by default and read incrementally. Pagination is capped at 1,000 pages by default, with an allowed configuration range up to 100,000, and cursor loops are rejected. Schema inference stops at 256 records by default. | `tests/test_http_source.py` | Partial. A page can contain many small records and normal record iteration has no total-record budget below the page limit. JSON structure depth and item count are not pre-scanned here. |
| Real network destination faults | Reset connection, lose an acknowledgement after commit, DNS delay or make a remote destination read-only | A localhost HTTPS endpoint commits an idempotency key, drops the real TLS connection before the response, then proves that the connector reports an unknown outcome and a same-key retry does not duplicate the commit. Simulated HTTP and database failures plus the local runtime lab cover adjacent state handling. | `tests/test_network_fault_lab.py`, `tests/test_http_source.py`, `tests/test_database.py`, `tests/test_workflow_failure_lab.py` | Partial. Real proxy-backed PostgreSQL and MySQL commits, DNS or latency injection and a read-only remote destination remain open. Local TLS and SQLite evidence are not substitutes for those systems. |
| Direct destination connector calls | Infinite or oversized caller-supplied batches | JSON stops at its structural item budget. HTTP streams one record per request. The database connector's dedicated atomic API requires a bounded sequence of at most 1,000 items and 64 MiB of corresponding sealed wire. Legacy CSV and generic database `write_records` calls can still materialize caller iterables. | `tests/test_json.py`, `tests/test_csv.py`, `tests/test_database.py` | Partial. The safe runtime uses the bounded API, but direct legacy connector calls do not yet share one count and byte contract. |
| Relay and outbox reads | One call loading an unbounded pending set | Lease and pending reads accept only 1 through 10,000 rows and at most 64 MiB of sealed wire by default. They walk the indexed queue order and stop before materializing or decoding the first record that would exceed the caller's byte budget. A relay lease lasts at most one hour, and malformed-record dead lettering is capped per call. | `tests/test_relay.py`, `tests/test_outbox.py`, `tests/test_recovery_stress.py` | Partial. Per-call memory is bounded, but there is no total row or byte quota for either persistent store. |
| Sealed quarantine spool | Full-table read from a negative SQLite `LIMIT` | `list_entries` accepts only 1 through 10,000 rows. Stored records retain the 64 MiB wire limit. | `tests/test_spool_limits.py`, `tests/test_workflow_failure_lab.py` | Partial. There is no total row or byte quota, retention policy or admission backpressure. |
| Operational event stream | Oversized events, malformed JSONL and unlimited local log growth | Input lines are limited to 4 KiB and compact writer output to 1 KiB. The stream is limited to 64 MiB by default and configurable only from 4 KiB through 1 GiB. Append and read check the limit under the cooperative path lock, and health CLI readers accept the matching explicit budget. | `tests/test_observability.py`, `tests/test_cli.py` | Covered for cooperative writers and bounded reads. There is no rotation; append fails closed when full. A process with direct write access can bypass the API. |
| Audit log | Payload leakage, chain tampering and unlimited database or export growth | Event fields are allowlisted and length bounded. Hash-chain verification and optional Ed25519 signatures detect stored-event modification. | `tests/test_audit.py`, `tests/test_source_auth.py` | Open for total rows, total bytes and streaming export. `verify`, `summary` and `export_jsonl` currently materialize the complete log. |
| SQLite durability stores | Corrupt or adversarial local database, disk exhaustion | SQLite durability settings and transactional state transitions protect crash consistency. Per-call reads are bounded where listed above. | `tests/test_sqlite_handles.py`, `tests/test_recovery_stress.py`, `tests/test_delivery_state_machine.py` | Partial. Disk quota, reserved free space and database page-count ceilings are deployment responsibilities today. Local host compromise is outside the threat model. |
| Optional semantic models | Model artifact replacement, unexpected model output and payload disclosure | Required assets and revisions are pinned, assets are SHA-256 checked, and model metadata files are capped at 64 KiB. Models receive descriptor text, not record values, and model scores cannot independently authorize an automatic mapping. | `tests/test_semantic_profile.py`, `tests/test_matching.py` | Partial. Model downloads and artifact hashing have no product byte budget. ONNX Runtime executes native code in the application process without a separate wall-time or RSS boundary. |

## Aggregate limits that are still missing

These are product gaps, not deployment footnotes:

1. Relay, outbox and quarantine storage need coordinated row and byte quotas. The quota design must
   include backpressure and an explicit durable state for rejected admission. Silently deleting or
   overwriting records would violate delivery guarantees.
2. Audit storage needs retention or archival plus streaming verification, summary and export. A
   byte cap that simply refuses the next audit event could also block delivery, so its failure
   semantics must be designed with the state machine.
3. CSV, generic database `write_records` and HTTP destination APIs need a common configurable batch
   count, per-record byte and total-work budget. The recovery runtime and dedicated atomic database
   path are bounded, but direct legacy library calls do not inherit those limits.
4. HTTP JSON source needs JSON depth and node-count gates plus a total-record option independent of
   pages. A response-byte cap alone does not provide a deterministic parse-tree RSS bound.
5. CSV destination updates currently read and rebuild the complete existing file. The admitted
   file size is bounded by the general 2 GiB file policy, but that is not a practical in-process
   RSS budget for a rewrite.
6. Normal CSV, JSON and Excel parsing must move behind the snapshot worker before the product can
   claim parser containment. The protocol needs bounded record frames and backpressure first.
7. POSIX `RLIMIT_AS`, `RLIMIT_CPU` and `RLIMIT_NPROC` are per process or real-user scoped rather
   than an aggregate worker-tree quota. Linux needs cgroup-v2 enforcement for a hard aggregate
   budget. Windows needs a Job Object for process-tree and resource control, plus AppContainer or
   an equivalent boundary for filesystem and network isolation.

## How to read benchmark evidence

The workflow and parser-worker benchmarks report wall time, CPU time and sampled RSS. Those values
are useful regression evidence, but measurements are not enforcement. A passing timing percentile
does not replace a byte, count or wall-time limit, and unit tests should not assert timing on shared
CI hosts. Strict parser-worker wall time and POSIX resource limits are enforcement; benchmark
numbers are observations.

Before a release, run the unit suite on Windows and Linux, the real Linux Bubblewrap lab, and the
workflow benchmark at multiple record and batch sizes. Retain the JSON benchmark reports as build
artifacts so regressions are comparable to the same hardware and dependency set.
