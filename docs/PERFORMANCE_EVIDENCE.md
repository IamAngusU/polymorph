# Public performance evidence

## The old 52.41 number and the newer checkpoints

The repository's `PERFORMANCE_BASELINE.md` records the completed 2026-09-10
pre-batching workflow: three 1,000-record, five-string-field runs, Python 3.11.9,
Windows build 26200, SQLite 3.45.1, DELETE journal, FULL synchronous mode.
Median throughput was 52.41 records/s and median peak RSS 85.42 MiB.
This is retained as history, not advertised as current throughput.

The owner's subsequent local orchestrator transcript reports seven intermediate
1,000-record runs between 351.06 and 355.79 records/s, median 353.52, maximum
95.23 MiB RSS, 1,000 commits and 1,000 verified audit entries in each run. It later
reports three preliminary runs around 381 records/s after another trust-cache
optimization. Further replay, spool and database-write-proof work happened after
those checkpoints, and the run stopped at the orchestrator's usage limit.

These are **development measurements reported by the owner**, not fresh runs
performed by this documentation change. Their final source digests, raw individual
reports and exact machine model are not present in this checkout. The README
therefore labels the seven-run result provisional and does not promote the 381
number to a final release claim. The 6.75x ratio between two summaries is not a
controlled before/after experiment on the final code.

Known user hardware (RTX 3080 10 GB and approximately 30 GB DDR5 RAM) is not
silently attached to a historical run that did not record those details. The GPU
is not used by the model-free SQLite workflow anyway. Do not invent an SSD model,
CPU, date-to-commit mapping or missing raw report hash.

## One table, multiple machines

`knowledge/benchmarks/*.json` holds one sanitized evidence document per campaign.
The README renderer combines them into ONE table, not one table per machine.
Add genuine runs from two or three device configurations when available. Historical
and provisional entries remain labeled; no empty hardware profile is sold as a run.

Record CPU model, physical/logical/usable cores and quotas; memory capacity and
observed RSS; storage class/model and filesystem; OS/Python/SQLite or database driver;
FULL durability and journal mode; model/knowledge identity (including `none`),
record shape, count, batch size, timing mode, repetitions and UTC date. CPU and
storage matter more than GPU for the current CPU/SQLite path.

Cold startup, warm filesystem cache, background load and observer overhead affect
comparability. More collected metadata is not proof of identical conditions.
Do not compare mapping fields/s, parser rows/s and fully durable delivery records/s
as if they described the same work.

## Export an actual lab workflow

Use the separate lab's `publish_benchmark.py` with a completed workflow report and
at least three repetitions. It rechecks retained raw workflow/gate evidence, exact
counts, audit/canary booleans, FULL durability and measurement agreement. It
exports an allowlist of hardware/version/configuration fields plus raw-report
hashes; not the entire local report or logs.

```powershell
python publish_benchmark.py .lab-state\reports\RUN_ID\report.json `
  --storage "operator-supplied SSD model / filesystem" `
  --out exports\workflow-20260911-workstation.json
```

Review the export, add it to `knowledge/benchmarks/`, then run
`python scripts/render_evidence.py`. The script updates both language READMEs
and local SVG badges. `--check` detects stale generated bytes. GitHub cannot run
arbitrary Python inside Markdown; automatic display follows the next reviewed
commit, not an invisible telemetry service.

A public counter must state its unit and source. Unique training queries, unique
positive/negative comparisons, optimizer updates and parser row executions are
separate quantities. Do not sum training counts across versions with overlapping
corpora and call the total new knowledge.

## Independent review and selected external ideas

The external discussions contributed useful prompts: lead with the import problem,
keep a clear evidence/authority distinction, use both malicious and legitimate
fixtures, make operator trust exchange understandable and split large modules by
security responsibility when doing a reviewed refactor.

They do not establish independent security certification. We do not adopt the
claims that all parser stages are sandboxed, every operation is signed, or one
CSV rule makes arbitrary spreadsheet applications safe. We do not add a
security-off switch. We also do not treat public uploads or crowd votes as correct
training labels. Public submissions need provenance, license/privacy review and
separate authoritative expectations. A file-drop is an input UI, not automatically
a bug-bounty program. No public upload service is implemented by this change.
